# 月影议事厅 UI 重设计：阶段 1

## 当前结构

- 前端是原生 HTML、CSS 与 JavaScript ES Modules，没有 React、Vue、路由库、构建器或客户端状态库。
- `web/index.html` 是唯一游戏页面；`web/app.js` 通过多个 `render*` 函数更新局部 DOM。
- `src/engine.js` 是唯一规则状态源。界面通过 `observe(HUMAN_ID)` 获取按身份过滤后的玩家、阶段、合法行动和事件。
- 浏览器只额外维护机器人实例、忙碌状态、模型状态和运行来源记录；大模型请求仍经 `/api/model/*` 服务端接口。
- 当前视觉集中在 `web/styles.css`，使用少量根变量，但仍有较多具体颜色、透明度和尺寸散落在组件规则中。

## 可复用与需要重设计的边界

可直接复用：游戏引擎、角色可见性、合法行动对象、公开事件、模型降级、渲染时机、ARIA live 区域、键盘焦点和减少动效支持。

值得重设计：顶部品牌与模式选择、阶段主视觉、玩家席位卡、行动面板、通知、公开记录、结果揭示。它们的语义结构可保留，视觉层和信息层级应逐个替换。

## 主要问题

1. 页面由相似矩形面板平铺，玩家席位、阶段和操作区缺少空间叙事，整体更像后台控制台。
2. 阶段差异主要依靠文字；夜晚、白天、投票和结算没有稳定的视觉语义。
3. 基础颜色虽接近目标方向，但变量命名偏具体，硬编码较多，难以统一悬停、选中、危险和禁用状态。
4. `.button`、`.player-card` 等样式直接与页面结构耦合，难以在后续组件中复用。
5. 字号、间距、圆角和阴影没有统一尺度；移动端虽可用，但触控尺寸不是所有控件的明确约束。
6. 已有焦点、live region 和 reduced-motion 是良好基础；后续需要继续做色彩对比、非颜色提示和键盘流程检查。

## 设计系统决策

- 色彩：以 `#0B1020` 为画布，`#171E30` 为主要表面；金色只表达主要行动和仪式感，银白承载正文，暗红表达危险，幽绿表达存活或成功。
- 排版：展示标题使用本地衬线字体栈，正文与控件使用本地无衬线字体栈，避免引入远程字体依赖。
- 间距：采用 4px 基础倍数；常用间距为 8、12、16、20、24、32、40、48px。
- 控件：桌面端最小高度 44px，移动端主要按钮 50px；所有操作必须具有 hover、active、focus、selected 和 disabled 状态。
- 面板：使用细边框、轻微顶边高光和有限阴影形成古堡空间感，不使用大面积纹理或高强度发光。
- 游戏语义：角色和阶段分别拥有语义 Token；颜色必须与文字、形状或状态标签共同出现。
- 响应式：保留 860px 与 640px 两级断点，下一阶段再根据玩家席位布局补充窄屏规则。

## 新增基础组件

- `game-panel`：标准、抬升、危险和安静面板。
- `game-button`：主要、次要、危险、弱化、选中和禁用状态。
- `game-badge`：身份、存活、出局和当前行动状态。
- `phase-heading`：夜晚、白天、投票和结算阶段标题。
- `game-field`：输入、文本域和选择器基础外观。

这些类目前集中在 `web/components.css`，通过 `web/design-system.html` 独立预览。主游戏继续使用原有类名，只接入 Token 和阶段数据属性。

## 下一阶段顺序

1. 重做阶段标题与页面氛围层，建立昼夜切换，但保留现有 DOM 和游戏流程。
2. 将玩家网格升级为议事厅席位系统，先处理存活、出局、真人、当前发言和合法目标五种状态。
3. 重做行动面板和目标选择，统一按钮、私密信息与发言输入。
4. 将公开记录改为可扫描的议事编年史，并增强投票结算的票型表达。
5. 最后重做结果揭示与复盘入口，再完成移动端、键盘、对比度和整局回归验证。
